# P14:事件流 seq + 重连补发 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 流式 AgentEvent 带 per-session 单调 seq;server 侧内存环形缓冲 + epoch;transport 断开**不再中断进行中的 turn**,事件继续产出进缓冲;App 重连时 init 携带 lastSeq/epoch,server 补发缺口或指示 `resync-required`(App 走既有 loadSession 全量重建);客户端按 (epoch, seq) 去重,断线期间事件不丢不重。Spec:`docs/superpowers/specs/2026-07-21-kimi-code借鉴五项改进-design.md` §5(契约条款 C14-1~C14-7)。

**Architecture:** 四层:wire(全事件可选 seq + init/session/resync 协议字段)→ server(新 `eventBuffer.ts`:seq 分配 + 环形缓冲 + epoch + **订阅表 fan-out**;messageHandler 改 publish 与 init 协商)→ client-core(serverConnection 游标/去重/缺口/resync 分发)→ app(resync → loadSession)。范围限流式 AgentEvent;`_reqId` RPC(file-list/sync-*)与 geek 模式(in-process,无传输层)不适用。

**Tech Stack:** TypeScript(ESM,`.js` 后缀)、zod v3(wire)、vitest(**不是 jest**)、pnpm workspace。

## 本计划新增决策(spec 未定或与实况冲突,执行前定死)

| # | 决策点 | 结论 |
|---|---|---|
| D-P14-1 | 事件如何到达"断线后重连的新连接" | **eventBuffer 承担 fan-out(per-session 订阅表)**。断线期间 turn 继续跑,旧连接的 send 闭包已死;`publish(sessionId, ev)` = 分配 seq → 入环 → 广播给当前全部订阅者(send 失败静默忽略)。spec §5.4 只写了"send 包装",未覆盖跨连接投递——没有订阅表,重连后只能拿到补发、拿不到进行中 turn 的后续实时事件 |
| D-P14-2 | 大事件截断 | **不截断**。spec 风险表的"result 16KB 截断副本"与 C14-2(补发逐字段相等)矛盾,C14-2 优先;改为**条数(2000)+ 字节(8MB)双上限整条淘汰**,淘汰导致的覆盖不足 → `resync-required(buffer-overflow)`(C14-4/C14-7 语义不变) |
| D-P14-3 | abort 控制器归属 | **移到 session 对象**(`AgentSession.currentAbort`)。现状是 handler(连接)局部变量(messageHandler.ts:57),断线重连后新 handler 无法停止旧连接启动的 turn——C14-6("断开不中断 turn")落地后这会成为"turn 不可停止"事故,必须同 PR 修 |
| D-P14-4 | 游标持久化 | **MVP 仅内存**(ServerConnection 实例内);App 冷启动无游标 → init 不带 lastSeq → 无补发,走既有 loadSession 全量加载(现状行为)。config 预留可选 `getEventCursor`/`persistEventCursor` 回调,宿主接入(RN settings / Web localStorage)后置 |
| D-P14-5 | 补发与订阅的时序 | **先订阅、后补发**:避免"session ack 后、订阅前"的事件真空(进行中 turn 随时在 publish);交错产生的重复由客户端 seq 去重兜底(C14-3 本来就要求) |
| D-P14-6 | 顺带修 error 分发缺陷 | serverConnection.ts:176 的 `case data.type === "error"` 把 AgentEvent 形态的 `{type:"error", message}` 改写成 `message: String(data.error ?? "unknown")`——真实错误文案被吞成 "unknown"(预存 bug,P12 后 error 事件更常见)。按字段分流:有 `message` → 原样 onAgentEvent;有 `error` → 控制错误路径(含 Unauthorized 停连逻辑不变) |

**Interfaces(Produces,T3 逐字消费):**

```ts
export interface SessionEventStream {
  readonly epoch: string;                       // 创建时生成 "ep_" + 随机,进程存活期不变
  readonly seq: number;                         // 最后分配的 seq(0 = 尚无事件)
  /** 分配 seq → 存入环 → 广播给全部订阅者(send 抛错静默忽略该订阅者)。返回带 seq 的事件。 */
  publish(ev: AgentEventType): AgentEventType;
  /** 注册实时投递回调;返回退订函数。 */
  subscribe(send: (ev: AgentEventType) => void): () => void;
  /** seq > fromSeq 的全部缓冲事件;覆盖不足(缺口已被淘汰)返回 null。 */
  readSince(fromSeq: number): AgentEventType[] | null;
}
/** 按 sessionId 取/建流(模块级 Map;30min 无 publish 自动清理,清理与 sessions TTL 同周期语义)。 */
export function getSessionStream(sessionId: string): SessionEventStream;
/** 测试辅助:清空注册表(setupFiles 隔离用)。 */
export function _resetStreams(): void;
```

**背景:** 实现要点——① seq 从 1 起严格 +1(C14-1);② 环形缓冲双上限:`MAX_EVENTS = 2000` 条 / `MAX_BYTES = 8MB`(按 `JSON.stringify(ev).length` 估算,入环时记录),超限从头部整条淘汰(D-P14-2);③ `readSince` 覆盖判定:缓冲为空且 fromSeq < seq → null;缓冲头部 seq > fromSeq + 1 → null(淘汰造成缺口);否则返回连续段;④ `publish` 存的对象与广播/补发的是**同一引用**(C14-2 逐字段相等的实现基础);⑤ epoch 用 `"ep_" + crypto.randomUUID()`(Node 20+ 全局可用);⑥ TTL:每次 publish 刷新 `lastActivity`,模块级 `setInterval`(5min)清理 30min 无活动的流(与 messageHandler 的 session TTL 常数一致);`.unref()` 防止测试进程挂起。

**背景与改动点:**

1. 实例态:`private cursor: { epoch?: string; lastSeq: number } = { lastSeq: 0 };`、`private gapStrikes = 0;`。`connect()` 时若 `config.getEventCursor?.()` 有值则采用。
2. **init 携带游标**:`sendInit`/relay 直连两处的 `{ type: "init", ... }` 构造,追加 `...(this.cursor.epoch ? { lastSeq: this.cursor.lastSeq, eventEpoch: this.cursor.epoch } : {})`(无 epoch = 从未收过带序事件,不请求补发)。
3. **session ack**:dispatch 的 `case "session"` 中,`data.eventEpoch` 存在且 ≠ `cursor.epoch` 时:若 cursor.epoch 为空(冷启动)→ 采纳 `{epoch: data.eventEpoch, lastSeq: data.currentSeq}`(此前事件不可得,交给宿主的常规历史加载);若非空 → 等 server 的 resync-required 决定(不自行猜)。
4. **带 seq 事件的守门**(dispatch 中 `AGENT_EVENT_TYPES.has(data.type)` 与 `tool-result` 流式路径,进入 onAgentEvent **之前**):

```ts
private admitSeq(data: any): boolean {   // true = 放行
  const seq = data.seq;
  if (typeof seq !== "number") return true;          // 无 seq(旧 server/geek):原样放行,游标不动
  if (seq <= this.cursor.lastSeq) return false;      // 重复(补发/广播交错):丢弃(C14-3)
  if (seq > this.cursor.lastSeq + 1 && this.cursor.lastSeq > 0) {
    // 缺口:第一次 → 断开重连(重连 init 带 lastSeq 走补发);第二次 → resync
    this.gapStrikes++;
    if (this.gapStrikes >= 2) {
      this.gapStrikes = 0;
      this.handlers.onResyncRequired?.("gap");
      this.cursor.lastSeq = seq;                     // 采纳现值,resync 后从此续
      return true;
    }
    try { this.ws?.close(); } catch { /* onclose 调度重连 */ }
    return false;
  }
  this.cursor.lastSeq = seq;
  this.gapStrikes = 0;
  if (data.type === "done" || data.type === "error") {
    this.config.persistEventCursor?.(this.cursor.epoch ?? "", seq);
  }
  return true;
```
